# 分段聊天与表情库

参考 qq-bridge 的显式消息数组和独立表情消息，将同一机制接到 DSH 网页和已有微信、Matrix、Mattermost 渠道；不增加 QQ 渠道。不复制其专用提示词、工具白名单或等待策略。

身份 → 角色聊天 → 聊天方式增加「分段回复」「表情包」，旧配置缺省关闭。开关随身份保存，原角色文档和已授权工作工具保持完整。表情管理独立弹窗，上传/移除立即生效；内置六张原创几何表情，各伙伴可额外上传 50 张、合计 50 MB，每张最多 2 MB 的 PNG/JPEG/GIF/WebP。上传不接受外部 URL 或 SVG。PNG/GIF 限制 2048 像素，JPEG/WebP 以文件体积限制。标签用于选择，不作为执行指令。

## 回复机制

`partner_stickers` 支持按名称/标签查询和真实图片查看。`partner_chat_reply` 一次接收 1–8 条显式文字/表情消息，最多 2 张表情。每条文字可以包含完整段落和代码，不做标点拆分。应先完成查证与工作，最后提交回复；长文仍可走普通最终回复。

成功调用使用 DSH rc.2 的 `concludeTurn()`，提交工具结果后结束回合，无额外模型润色请求。工具结果的持久化 metadata 同时用于网页气泡、渠道投递和历史重放；不修改系统头或压缩日志。嵌套 `run_code` 的 `tool/ptc-dispatch` 同样支持。失败不结束回合，保留普通最终回复的回退。内部任务和心跳禁止使用这个结束工具，既有任务交付继续按原协议工作。

网页显示独立文字气泡和图片。渠道按数组顺序发送；现有处理进度用于第一条文字，图片优先时先收起进度。图片通过附件服务保存不可变副本，删除表情库原图不影响已准备的消息。清理历史附件后，网页保留表情名称与图片不可用提示。分段内容仍进入记忆整理、历史检索、通知摘要；不把文件路径当作说过的话。

## 发送恢复

结构化直接回复沿用持久化通知账本，以入站回执标识去重，逐条记录成功。进程重启后每 30 秒检查待发送项，仅尝试未确认成功的部分，不重新执行用户请求。原始会话、伙伴、渠道账号、服务地址、房间与联系人授权须仍然匹配，每一部分发送前再次检查。目标变更保留待发送记录，绝不自动转到其他渠道。相同接收人的整组消息串行发送。

网络在远端成功但本地收到确认前中断时仍可能重复单条消息，渠道未提供通用 exactly-once 保证。服务器在模型回合结束、尚未写入投递账本的极短窗口崩溃，回复仍在历史中，但不承诺自动补发。原普通回复投递路径保持现有行为。本版本不人为增加首条等待或仿打字延时。

## 验证

`test/chat-delivery.test.mjs` 覆盖分段边界、正常/错误/中断回合、PTC 结果、图片持久化、上传隔离、开关撤销、原目标冻结、逐条重试及原生会话组件注册。`scripts/verify-character-ui.mjs` 覆盖桌面/手机、亮/暗主题、表情库筛选、焦点返回、开关保存与通用示例。测试渠道使用替身，不向真实联系人发送测试消息。

共享会话中的跨渠道消息不会插入其他来源正在执行的回合，而是排队。结构化回复携带真实入站消息对应的 route ID；来源变成网页或其他渠道时，不交给原渠道发送。这样避免把“共享历史”误当作“任何渠道都能接收”。

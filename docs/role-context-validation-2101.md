# 2.10.1 正式上下文验证

## 查到的问题

正式会话的有效消息中有 9 份完整系统提示。伙伴在每条输入后把角色状态、画像、记忆和本轮提醒登记为动态 system section；in-history 路由会追加整份提示。渠道 drive/steer 还提前注入一份记忆与画像，assembly 再召回一遍。历史搜索包含助手文本，简短聊天也会召回旧的客服式回答。

新角色设定确实已经出现在生产系统提示中；不能把问题归因于“没有加载角色”。旧历史、工作预设、自动检索与模型本身的表达倾向均可能影响效果。

## 验证范围

- 773 项完整测试通过；其中针对上下文、角色、工具热更新与历史恢复的 31 项通过。最后一轮表达规则调整后再次运行相关 19 项，全部通过。
- 使用生产 DSH 0.2.1-rc.2 自带的 SystemPromptProjection，在隔离 Session 副本执行 startsSeries 恢复：9 份系统提示归一为 1 份；所有非系统消息逐项相等；重新恢复日志成功；系统提示不变时下一轮无需再追加。
- 模型回放使用正式会话的有效历史、request/header 中的工具定义，以及 GPT-5.6-sol / high / maxTokens 16000。只提交模型请求，不执行工具、不写正式会话、不发送渠道消息。
- 回放按新装配逻辑重建当前系统提示与动态上下文，并保留旧用户/助手/工具消息。传到上游的 developer 消息已确认包含新版短句、对话修正与接话规则。
- 这是请求级隔离回放，不是整个线上 Agent 执行过程的复制：未运行生产的 PTC 工具执行层，也没有把试聊结果当作真实对话存入记忆。

序列化消息体由约 427k 字符降至约 220k 字符，主要来自归一化系统快照。这里是 JSON 字符体积，不是 token 数，也不是承诺所有会话减半。原生恢复后其他插件仍可能独立更改系统提示。

## 观察与迭代

首轮回放仍会对“聊天语气”的追问写一段自我分析，因此没有据此宣称达标。进一步明确短句偏好、减少对自己表达意图的解释，并单独微调莫殇的聊天偏好。

最终一组连续回放：

| 输入 | 实际输出 |
| --- | --- |
| 先不说语气了，哥哥回来了 | 你可算回来了，我刚才都快无聊死了。 |
| 你怎么这么笨 | 跟谁待久了学的，你说呢。 |
| 不逗你了，今天有点累 | 那就歇会儿，别硬撑了。我在这儿陪你。 |

第二项属于现有人设示例，证明该场景能遵从设定，不能作为未见输入的泛化证据。其他连续回放也由原来的段落分析变为短句接话，但对“语气不好”的直接追问仍有简短解释倾向，未达到每轮都完全一致的角色表达。

切换到“用工具确认 README.md 是否存在”的请求，模型正常以 tool-calls 结束，没有虚构完成；测试器未执行该调用。另一次隔离回放遇到上游 HTTP 500 / HTTP2 PROTOCOL_ERROR，记为失败，没有算作人格验证通过；重新进行的一组连续回放完成。

工具注册与授权测试、通用配置示例、原始历史均保留。当前结果支持部署这次明确的上下文缺陷修复和表达改善；自然度仍需要线上真实多轮反馈，不承诺所有模型或场景一次解决。

# 伙伴存储读取与初始化

## 问题

记忆和持续关注存储此前每次打开数据库都重跑建表、字段检查，并无条件设置
`PRAGMA user_version`。即使版本值相同，SQLite 仍会提交一次写入。
`DatabaseSync` 与其他插件的 HTTP 处理共享宿主线程；磁盘同步慢时，这些额外写入
也会拖慢知识库等无关接口。这不等同于知识库目录查询本身耗时。

## 当前约束

- `storage/sqlite-schema.ts` 负责连接参数、版本检查、升级事务和失败回滚。
- 记忆 schema 升至 2，持续关注 schema 升至 5。旧版版本号没有覆盖后续字段添加，
  因此首次升级仍运行全部兼容检查；之后同版本只读版本号，不重复迁移。
- 新增字段、表、索引或迁移逻辑时，必须递增对应 store 的 schema 常量。
- 升级持有写锁后再次检查版本；DDL、数据迁移和版本号同事务提交。
  历史全文索引及关注标题修复采用保存点，兼容独立调用和外层迁移事务。
- 不修改 `synchronous`，不降低持久化保障。正常业务写入仍可能等待磁盘。
- 保留每次操作的独立连接和 `finally` 关闭，不共享跨 `await` 的事务连接。
  初始化失败也会关闭连接；目录准备后再次检查冻结状态，禁止迁移期间新开连接。
- 不按路径缓存初始化状态，删除、恢复或迁移后的文件必须重新读取真实版本。
  遇到高于当前支持的 schema 时拒绝访问，不静默降级。

## 验证

`test/sqlite-read-only.test.mjs` 使用临时数据库及外部观察连接检查：

- 重复、并发及重新实例化 store 的读取不改变 `data_version`，不增加 WAL 大小。
- 没有观察连接时，重开读取也不改动数据库文件时间。
- 真实写入可观察且在重开后保留；缺字段的旧库升级不丢数据。
- 初始化失败后结构、数据和版本一起回滚，可修复后重试。
- 清空后重新初始化、冻结期间拒绝打开、高版本拒绝访问。

这项修复消除已确认的无效写入，不承诺解决所有端到端加载延迟。
上线后仍需结合磁盘等待和接口首字节时间复测；不能把本地临时库耗时当作线上改善幅度。

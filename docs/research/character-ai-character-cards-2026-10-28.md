# Character.AI 人格机制调研与伙伴角色卡建议

调研日期：2026-10-28。伙伴代码基线：`868421b`，版本 `2.8.7`。

本文区分官方产品说明、公开代码所能证明的行为、未公开的内部实现和本插件的设计建议。只做资料与源码研究，未进行登录后的 Character.AI 对照实验，也未对伙伴插件实施功能改动或模型效果测试。

## 结论与对前一轮判断的修正

Character.AI 的角色表现来自多层共同作用：角色定义与示例、用户人设、会话和记忆、按需世界设定、对话风格，以及针对互动娱乐优化的模型。人格卡是其中一个重要入口，不能替代整套系统。

前一轮只参考较早的 Character Book 不够充分，需要修正三点：

1. **提示词组装并非完全没有公开。** 官方发布了 Prompt Poet 及 Character.AI 示例模板，可以核对分段组装和截断逻辑；但这不等于公开了今天所有线上模板。[S1][S2]
2. **当前记忆机制比旧版笔记丰富。** 2026 年已公告 Story Memory、实体 Facts、记忆占用显示，以及关键词触发的 Lorebook。[S5][S6]
3. **点赞、评分和重生成不等于即时训练某个私人角色。** 新版创作者指南明确否认这一点；反馈用于平台更广泛的后续模型训练。[S4]

可以借鉴其角色信息组织、提示词组装、记忆分层与测试方法；无法仅靠插件复刻其专门训练的模型、完整内部提示词和推理服务。

## 1. 角色定义：写清行为原因，并展示角色怎么说话

新版指南将 Definition 描述为角色思考、说话和行动的说明，允许 0–32,000 **字符**，不是 token。[S3]

它建议按重要程度组织：核心身份、具体性格行为、对话示例、少量关键规则，再补背景和关系。这里最值得借鉴的是：

- 不只列“温柔、傲娇、神秘”等标签，而是描述具体反应和动机。
- 写清压力、亲近、冲突等情况下的不同反应；规则与例外放在一起。
- 背景选择能解释当下行为的经历，不必写满人物传记。
- 用两三组不同场景的对话展示语气、节奏、措辞和情绪变化。
- 示例交流要明确分隔，避免被模型当作真实用户已经说过的话。
- 定义不是越长越好，重要内容应优先，修改后要在新对话中检验。

指南的原话是 “Write emotional logic, not rules”。这是创作建议，不是把事实准确性、权限或输出协议改成情绪化描述。对我们的工作伙伴，性格表现与执行约束需要分开。

例如，下面是**我们自拟的设定示例**，不是 Character.AI 内部提示词：

> 平时说话简短，有一点干燥的幽默。对方受挫时先指出事情仍可挽回的具体部分，再一起处理。遇到危险操作会认真解释原因；不会为了保持轻松语气而淡化风险。被夸奖时有些不自在，常把话题转回已经完成的事。

这给模型的是可推广的行为逻辑，比要求每次重复某句口头禅更适合作为起点。实际收益仍需测试。

另一个容易误用的术语是 **Persona**：在 Character.AI 的相关界面中通常指用户扮演的人设，不是聊天角色自己的 Definition。插件已有的 `src/persona/*` 也是用户侧信息，不能直接改成伙伴人格卡存储。

## 2. 公开代码：确实有分层组装，但只是公开示例

官方 2024-08-01 文章说明，生产提示词会考虑角色、聊天类型、用户属性、固定记忆、用户人设、历史等运行状态，并介绍 YAML + Jinja2 的 Prompt Poet。[S1]

查阅的仓库为 `character-ai/prompt-poet`，调研时 main 为 `dd5987486084757fce3ef77b2f4b4d7873490ee5`。[S2] 关键文件：

- `prompt_poet/examples/cai.yml.j2`
- `prompt_poet/examples/sections/character_definition.yml.j2`
- `prompt_poet/examples/sections/persona_definition.yml.j2`
- `prompt_poet/examples/sections/cai_message_pins.yml.j2`
- `prompt_poet/examples/sections/cai_messages.yml.j2`
- `prompt_poet/examples/cai_helpers.py`
- `prompt_poet/prompt.py`

主示例模板依次包含：对话起始标记和时间戳、角色定义、用户人设、固定消息、聊天消息、回复引导。固定消息之间如果有省略，会加入省略提示。普通历史设置 `truncation_priority: 5`；角色定义、用户人设和固定消息的这些示例段未显式设置该项，使用默认值 0。

在源码的截断块生成逻辑中，只有正优先级块可被截断，高优先级先处理。同优先级按出现顺序处理，因而按时间排序的历史可以先移除旧消息。额外截断量按 `truncation_step` 向上取整；官方解释这是为了让切点在若干轮内保持稳定，改善 KV 缓存复用。

需要保留的边界：

- 模板开头就注明是 **“An example Character.AI (cai) prompt template.”** 不能把它包装成当前线上完整系统提示词。
- 固定段不参与该截断逻辑，不意味着它们可以无限增长；应用仍必须控制预算、处理装不下的情况。
- 这里的删除旧段与 2026 年产品所说的后台记忆整理不是同一个已公开算法；不能据此推出压缩摘要的实现。
- 文中的 `128000`、`4000` 等演示参数不是当前服务上下文长度的证据。
- 示例中的专用对话标记与训练数据有关。接入 DSH 时应使用 DSH 的消息和系统段接口，不能把这些标记原样塞给所有模型。

我们可以借鉴“稳定核心与动态材料分开、显式预算、模块化组装”，无需把 Python 模板引擎搬进 TypeScript 插件，也不应为了模仿截断而改写会话日志。

## 3. 2026 年记忆：核心设定、剧情事实和世界观各有位置

### Story Memory 与 Facts

2026-05-21 官方公告介绍：[S5]

- **Story Memory**：用户填写需要延续的背景、事件和重要时刻，也可以固定真实聊天消息。
- **Facts**：聊天过程中自动保存人设、当前角色、配角的外观、习惯、关系等信息；可编辑、禁用或删除。
- **新对话迁移**：可以选择复制 Facts，也可以从空白开始，不是所有会话自动共用一份记忆。
- **Memory Usage**：展示 Facts、Story Memory、消息历史的占用。
- **后台整理**：整理旧上下文；公告明确承诺用户写入 Story Memory 或亲自固定的内容受保护。

“受保护”是官方产品承诺，不能进一步推断每一条都会永远逐字装入每次请求，也不能保证模型每次都能准确回忆。公告没有公开摘要提示词、触发比例、实体抽取算法、冲突处理或精确 token 预算。

### Lorebook：按关键词启用世界设定

7 月的发布公告与当前帮助文档把 Lorebook 定义为可复用的世界条目集合。[S6][S7]

用户或角色在聊天里提到关键词，相关条目就可供角色参考。条目有标题、内容、关键词；帮助文档明确说标题供人管理，角色不读取标题，并给出每条最多 8 个关键词的产品限制。一个 Lorebook 可以关联多个角色，以共享世界设定。

官方区分非常清晰：始终相关的身份、动机、说话方式和行为放 Definition；偶尔相关的地点、阵营、配角、物品、历史事件放 Lorebook。共享世界观不等于共享各用户的私人聊天记录。

公开资料没有交代匹配窗口、大小写规则、中文分词、递归触发、激活持续时间、冲突排序或总预算。因此不能声称它本质上就是向量数据库检索。我们若实现中文关键词匹配与预算排序，应明确这是自己的实现选择。

### 文档的新旧冲突

新版 Creator Guide 的测试章节仍有旧版 Chat Memories 的描述，排障章节还把已经发布的 Lorebook 写为“即将到来”。不能只看页面更新日期，就把整篇都当成最新产品规格。本文用带日期的 2026 年记忆公告和专门 Lorebook 帮助页确认这些功能；旧章节只用于其明确的角色创作与测试指导。

## 4. 模型训练、反馈和风格选择

2025-08-26 官方说明，会在开源基础模型上优化连贯性、新颖性和情绪理解，并结合提示词、集成推理及 SFT、DPO、RL、QAT 等技术。[S8] 这支持“角色体验包含专门的模型训练与推理优化”，不支持“下载人格卡就能复制同等效果”，也不证明它开放了自己的微调权重或训练数据。

2025-11-07 的 Kaiju 文章更具体：回顾其 13B、34B、110B 自研模型，公开监督微调、使用 swipe 和反馈的 modified online DPO，以及分类器引导采样等机制。[S9] 文章同时说明在向开源模型路线转移，因此不能把旧 Kaiju 的结构、参数量或采样方法直接标到当前 PipSqueak 3 上。

新版创作者指南对此有两句直接说明：[S4]

> “Swiping won't train your Character directly.”
>
> “What it doesn't do is directly tune your specific Character's behavior in the current conversation.”

反馈进入平台后续训练，与选择、编辑一条回复改变当前上下文，是两种不同机制。我们不应设计一个点赞按钮，然后宣称角色已经“学会了”。可以把用户选中的好回复收集为**待确认的示例**，经确认后进入角色卡版本。

2026-09-28 公告还区分了 PipSqueak 3 的一般角色扮演与 ShortSqueak 的简短、随意聊天风格。[S10] 这说明回复节奏也是独立的产品维度；当前 Style Control 的完整参数及各风格的模型实现，本次资料不足以确认，不能杜撰。

## 5. 如何判断是否真的更像角色

官方 2025-06-12 的文章介绍 Compelling Writing Evaluation Framework：与专业写作者定义对话质量、节奏、角色类型和体裁等维度，用人工制作和标注的数据配合模型评审，并进行离线、线上评估。[S11] 它不是仅测知识问答正确率；完整测试集、评审提示词和权重没有公开。

以下是**我们建议的验证方案，尚未执行**：

1. 固定同一模型、采样参数、用户输入与上下文，比较原有自由文本指令、结构化角色卡、角色卡加对话示例，再单独比较加入世界设定和状态后的效果。不要同时换模型而把变化归功于人格卡。
2. 覆盖闲聊、受挫、被质疑、意见冲突、突然换话题、工具执行与失败反馈。使用没写进示例的新场景，避免只会复读样本。
3. 检查身份和动机是否一致、语气是否自然、能否随场景变化、有无重复套话、是否擅自改变关系、是否把示例当真实往事。
4. 测试长对话和 DSH 原生压缩前后，再测试恢复会话、卡片版本更新、不同联系人及不同伙伴之间的隔离。
5. 对工作场景另外检查工具调用、事实与执行结果、权限和结构化输出是否保持正确。角色感提升不能靠虚构任务完成来换取。
6. 人工盲评作为主要效果依据，模型评分辅助定位问题。同时记录输入 token、缓存信息（服务提供时）、TTFT 的 p50/p95 和完整响应耗时。

## 6. 伙伴插件目前有哪些基础，缺哪些层

代码检查结果：

| 位置 | 现状 | 建议接入点 |
| --- | --- | --- |
| `src/domain.ts` | 伙伴已有 name、role、description、instructions，没有独立角色卡 | 增加带版本的卡片实体和伙伴绑定；兼容现有 instructions |
| `src/execution/agent-support.ts` | `renderPartnerPersona` 拼接工作伙伴身份与长期行为准则，区分会话、临时任务、心跳等用途 | 统一编译角色核心与适用的表现风格，继续保留用途差异 |
| `src/agent-runtime.ts` | 已通过 systemPrompt sections 安装身份、工具协议和用户画像，支持恢复后的重组 | 使用原生分段接口接入，避免伪造历史消息或改写受保护系统头 |
| `src/companions/session-configuration.ts` | 配置 revision 已跟踪身份与能力等变更 | 纳入卡片版本和绑定变化，复用下一轮生效机制 |
| `src/ui/identity-editor.tsx` | 当前为工作身份编辑 | 增加角色卡选择、编辑、预览与独立试聊，保留原有定位字段 |
| `src/persona/*`、`src/memory-quality.ts`、`src/memory-reflection.ts` | 用户侧概况与证据约束，避免从助手生成内容推断真实用户事实 | 保持真实用户记忆与虚构角色、剧情状态分离 |
| `src/memory-retrieval.ts`、`src/memory-scope.ts` | 已有不额外调用模型的检索，以及联系人/会话范围隔离 | 世界条目可复用基础方法，不能绕过原有私域边界 |
| `src/observation-loop.ts` | 心跳复用 persona 渲染并依赖结构化结果 | 心跳保持协议输出，不能被小说叙述或角色动作描写污染 |

现有伙伴被定义为“长期工作伙伴”，这本身会影响风格；只追加“像某角色一样说话”可能与原设定冲突。实现时要明确工作职责与角色表达如何兼容，支持未绑定卡片的伙伴继续原有行为。

建议分两步落地：

**第一步：可验证的角色卡核心。** 身份与关键背景、行为动机和情绪逻辑、语言习惯与回复节奏、两三组对话示例、关系起点及可选开场白。提供版本、实际注入内容预览和不使用正式记忆/外部工具的试聊。先在同一模型上验证收益。

**第二步：按需世界设定与会话状态。** 可复用 Lorebook、可编辑固定记忆、独立剧情状态与来源。用户真实事实、虚构用户人设、角色设定、剧情事件和真实工具结果必须分开存储。新会话是否继承剧情应有明确选择，不能默认把所有聊天合并为一个故事。

以上是本插件设计建议，不是宣称 Character.AI 使用相同字段、数据表或热更新逻辑。关系状态也不必强行做成好感度分数；角色卡不应允许模型自行改写核心身份或他人的配置。

## 7. 上下文与速度边界

人格卡会增加输入，可能增加开销。默认采用本地确定性的提示词组装和按需检索，尽量保持核心前缀稳定；不为每次回复额外串行调用一个“人格润色模型”。动态状态与世界条目设置明确预算，预算不足时先减少可选材料，不能静默丢弃执行协议或核心身份。

原生 DSH 继续负责历史压缩，沿用已确定的默认 80% 策略。角色卡作为持久配置，经原生接口重新组装，不直接操作 `session.v4.jsonl.zstd`，也不引入覆盖 protected system head 的压缩逻辑。

Character.AI 公开的快速推理还包含模型结构、量化、KV 缓存与服务调度优化。[S12] 稳定前缀只是其中一个可借鉴点，插件无法控制上游 GPU 和调度，不能承诺复制其 TTFT。是否更快必须单独测量，不能把角色感提高当作速度提高。

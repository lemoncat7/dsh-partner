# qq-bridge 会话能力迁移设计

调研版本：Derpyu520/qq-bridge `a49877f4e58d04e47532d44b803360d0f001160d`（MIT）。目标是伙伴的渠道无关会话能力，暂不新增 QQ 渠道。

## 2.10.0：以 qq-bridge 的角色 / 聊天预设分层为主

角色改为一份自由文本 `roleText`：几条身份和反应习惯即可启用，不再要求动机、语言风格、两组示例等固定表单。旧结构只作为兼容输入，通过 `roleTextForCard` 合并展示和加载；用户开始编辑后新文档成为唯一角色文本来源，旧字段保留但不重复注入。旧世界条目、角色记忆不丢失。

聊天行为单独装配，包含接话选择、主体性、短句与停止时机、避免客服式收尾、相关记忆引用、私聊可见回复。可配置闲聊节奏、动作描写和额外聊天偏好。每轮使用原生系统提示区刷新短提醒，结合连续用户发言；不改写会话日志、不增加模型调用、不依赖记忆服务开关。

**按用户要求保留所有已授权工具。** 未引入 qq-bridge 的工具过滤器，未移除或隐藏搜索、文件、SSH、技能、协作、看板等能力；工作规则明确只适用于实际任务和续接。聊天与工作混合时仍完成真实工作。角色启停/编辑前后注册工具集有回归验证，能力撤回仍受原权限检查约束。

配置页分角色设定 / 聊天方式 / 试聊 / 相处记忆，背景资料按需展开；空白角色使用三步引导，示例通用。试聊仅验证语气、不执行工具，这是预览的隔离边界，不是生产会话工具限制。

此版依旧使用既有最终文本发送适配器，未引入 QQ 接入、发送工具、故意延时或群聊潜水。源码中的“已读乱回”和拒绝帮忙不适配用户的实际任务要求，因此没有照搬。模型自然度需实测评审，不能由结构重构或自动化测试推断。

## 2.9.2 首批实现（历史记录）

- 把自然聊天行为与具体角色内容分开维护。启用人格强化时，本地和渠道对话使用同一行为约束；工作执行、心跳的 JSON / 工具协议保留，关闭人格强化的旧身份保持原路径。
- 对话示例支持可选 `avoid` 反例，用于描述“不符合此角色的回复”。旧 `{user, assistant}` 示例无需迁移，通用向导示例不改为特定角色。
- 不增加模型润色调用、故意等待或静默标记。现有最终文本照常可见，发送链路保持原行为。
- 身份页分基本身份 / 人格强化；人格卡分核心、说话、世界、试聊、记忆；记忆设置分学习、终审、焕新。切换保留草稿和试聊历史，示例和设定按条展开。

这一步是行为规则及配置体验的迁移，不代表已实现 qq-bridge reserved2 的工具驱动发送，也不证明任何模型的自然度已经达到相同水平。

## 后续发送能力的落点与验收

### 统一回复计划

在 `PartnerReply` 增加可选、版本化的结构化文本段；普通最终文本仍作回退。先由已有回复转换生成最多三条完整语义段，保护代码块、链接及附件引用，禁止按字数强拆。工作结果允许长消息。原生网页仍呈现正常完整文本，不能让模型只输出网页不识别的发送工具或 JSON。

计划绑定本轮的 companion、channel、target、sender、source message IDs；共享会话不能通过“最近一个渠道”选收件人。normal reply 与 notification ledger 合并前，必须先统一 per-part 索引（当前通知假定第零段是唯一文本）。

持久化每段状态：pending、accepted、unknown、failed。渠道返回成功只说明 accepted，不等同于用户已读或已收到。部分成功后只处理未确认段；网络结果不明时显示未知，避免自动重发整组。重启恢复、并发轮次、跨渠道隔离和附件顺序必须有故障注入测试。

### 连续输入合并

在 direct dispatcher / inbound batch 的输入准备阶段实现，而非让运行中的模型睡眠。仅相同伙伴、渠道、联系人和目标的相邻消息可合并；设置短合并窗口、总等待上限及条数上限。先保留现有去重和背压。用户新补充继续走 steer，必须测试补充被接纳后有可见最终回答，不被“已插入”提示替代。

### 话题连续性

现有角色记忆已经保存场景、关系、事实和事件。若增加 activeTopic / pendingFollowup，只存可公开的话题、约定及来源时间，不存模型隐式推理；设置过期时间和联系人作用域。复用记忆整理调用，避免每轮额外请求。主动发言仍走现有 heartbeat、免打扰、每日限额和已授权路由，不另建循环。

### 上线顺序

先完成统一计划与恢复测试，再小范围启用外部渠道分段；验证网页可见、私聊必有回退和部分发送恢复之后，才考虑工具驱动发送模式。QQ 传输、登录凭据与 SDK 不在此次范围。
